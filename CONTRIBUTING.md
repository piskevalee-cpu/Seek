# Contributing to SEEK

Thanks for helping. SEEK is a small harness with strict contracts; this file gathers the rules
that are otherwise spread across `docs/SPEC.md` and `AGENTS.md`. When this file and the
specification disagree, the specification wins — it is the source of truth.

## Before you start

- Read [docs/SPEC.md](docs/SPEC.md), especially §0 (precedence), §2 (workflow and versioning) and
  §15 (milestones). Work only on what the current milestone allows; do not pull later features
  forward.
- Rust 1.88 or newer. `git` is needed for the `git` widget; the `llama` binary is needed only for
  local models.
- Check the open issues first. One task, one branch, one pull request.

## Branching and pull requests

| Branch | Start from | Merge into | Use |
| --- | --- | --- | --- |
| `main` | — | — | Always releasable; only releases and hotfixes land here. Every release is tagged here. |
| `develop` | `main` | `release/*` | Integration branch; CI must be green. |
| `feature/<scope>-<desc>` | `develop` | `develop` (squash) | One feature or milestone item. |
| `fix/<desc>` | `develop` | `develop` (squash) | A fix for something not yet released. |
| `release/<x.y.z>` | `develop` | `main`, then back to `develop` | Version bump, changelog and final fixes only. |
| `hotfix/<desc>` | `main` | `main` and `develop` | Urgent fix to a released version; bumps PATCH. |
| `docs/…`, `chore/…`, `refactor/…` | `develop` | `develop` | Non-feature work. |
| `experiment/<desc>` | `develop` | never merged | A spike; port the good ideas into a `feature/` branch. |

Never commit directly to `main` or `develop`, and never force-push or rewrite shared history.
Keep commits small: each one builds and passes its tests. Open the pull request against `develop`
and say in its description:

1. what changed, and why;
2. which section of `docs/SPEC.md` it implements;
3. how it was tested (commands, and any manual checklist items you walked);
4. whether a contract or a schema version changed.

## Commit messages

Use Conventional Commits:

```
<type>(<scope>): <short imperative subject>

An optional body explains the why, not the what.
```

- **Types:** `feat`, `fix`, `docs`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`.
- **Scopes:** `tui`, `core`, `llm`, `local`, `tools`, `skills`, `widgets`, `install`, `docs`.
- **Example:** `feat(local): stop the server before a model switch`.

## Versioning

- SemVer, tags `vMAJOR.MINOR.PATCH`. The workspace has one version in
  `[workspace.package]`; `seek --version` prints it with the short git SHA.
- Before 1.0: a MINOR ships a milestone (SPEC §15) or a breaking contract change; a PATCH is a
  fix. Pre-releases look like `v0.8.0-alpha.1` or `v0.8.0-rc.1`. From 1.0 on, breaking a contract
  requires a MAJOR.
- The **contracts** are the `~/seek/` layout, `tool.toml`, `widget.toml`, `providers.toml`,
  `config.toml`, the per-model sidecar `.toml`, the session JSONL format, CLI flags and slash
  commands. Every file format carries `schema = 1`; a change needs a migration, a version bump
  and a changelog note. The contracts freeze at 1.0.0.
- `CHANGELOG.md` follows Keep a Changelog and is updated on the release branch. Add an entry
  under `[Unreleased]` when the change lands on `develop`.
- A tag `v*` triggers the release workflow, which builds the binaries and attaches them to the
  GitHub Release with the changelog notes. Do not bump the version in a feature pull request.

## Before you push

```sh
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace -j 2
```

If a local llama.cpp server is running, keep `-j 2`: this machine has 15 GB of RAM and no swap,
and a parallel build can exhaust it. Start a test server with a small context (`--ctx-size 4096`).

A change to the UI, the tools or the agent loop also needs a walk through
[docs/TESTING.md](docs/TESTING.md). Unit tests do not cover the layout, the keyboard or the flow
of a conversation.

## Rules that break the spec if ignored

- The system prompt plus the default tool schemas must stay under 1,500 tokens
  (`crates/seek-core/tests/prompt_budget.rs`).
- Every fact has exactly one home (SPEC §10.2). The `usage` widget and the METRICS block are
  different scopes, not a duplicate.
- Keep the prompt prefix stable and append-only so provider caches and llama.cpp `cache_prompt`
  reuse keep working.
- Offer only the reasoning variants a model's catalog declares (SPEC §9.7).
- API keys never go in `config.toml` or `providers.toml`: use an environment variable name or
  `state/auth.json` (mode 0600), and redact them wherever they could be logged.
- `install.sh` is idempotent and never overwrites a user file in `~/seek/`.
- Keep `panic = "unwind"` in the release profile: llama.cpp server cleanup relies on `Drop`.
- The logo bitmap is generated by `tools/extract_logo.py`; regenerate it after changing
  `assets/logo.png` and never scale the PNG at runtime.
- Ported code keeps its upstream attribution: oh-my-pi is MIT, grok-build is Apache-2.0.

## CI and reviews

Every pull request runs formatting, clippy with warnings denied, all tests, a build on Linux and
macOS, and the prompt-budget test. A change to a contract or to the prompt prefix needs an
explicit note in the pull request so the reviewer can check the migration. There is no license
yet (D-005); ask the owner before adding one.
